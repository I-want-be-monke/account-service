# Нагрузочные сценарии E11

Генератор работает на Java 21 из CMD. Он сохраняет сырые замеры в CSV JTL и рассчитывает метрики сам. В отчёте учитываются только выполненные испытания и фактический размер стенда.

Перед нагрузкой подготовьте отдельный проект Compose `account-service-e11`, PostgreSQL `account_service_e11`, том `account-service-e11_account-data` и синтетический набор E11. Генератор сверяет контейнеры `app` и `db`, сеть проекта, том, привязку HTTPS на `127.0.0.1:18448`, адрес PostgreSQL в конфигурации приложения и фактическое имя БД. URL задан в коде. Порт 18449 предназначен для второго экземпляра при проверке SCALE-01.

По умолчанию скрипт ищет `.local\e11\stand.env`, `.local\e11\tls.p12` и `.local\e11-verification\fixtures.csv`. Параметры `--env`, `--tls` и `--fixtures` позволяют указать другие локальные файлы. TLS-проверка использует сертификат `accounts-local` из указанного PKCS12 и обычную проверку имени `localhost`. Секреты читаются из локального файла и используются только для входа и открытия PKCS12. Для каждой роли берётся её `DEMO_*_PASSWORD`, соответствующий хэшам синтетических пользователей.

Проверка готовности перед испытанием выполняет HTTPS readiness и чтение PostgreSQL. Она сверяет роли, клиентское владение и выделенные для нагрузки счета с файлом fixtures. Месяц с нулём проведённых операций отклоняется.

```bat
cd /d C:\vyz\incheneria\account-service
scripts\load-test.cmd --check --report-month 2026-10
```

Полный профиль с 300 пользователями запускается на стенде с подготовленным набором из 200 000 счетов и проверенными ресурсами. Команда задаёт три независимых прогона, 300 секунд разгона, 300 секунд прогрева и 1 200 секунд стабильного измерения в каждом. Месяц должен совпадать с согласованным насыщенным периодом синтетического набора.

При запуске на 300 пользователей генератор требует не менее 4 vCPU, 8 000 000 000 байт эффективной памяти Docker, ровно 200 000 счетов и минимум 1 000 000 проведённых операций. Генерация профиля `pilot` также проверяет минимум Docker до записи. Обычный `--check` остаётся проверкой конфигурации стенда и набора. Для формальной приёмки используйте одинаковый исходный снимок перед каждым из трёх прогонов. [Перенос и протокол пилота](../../docs/pilot-stand.md)

```bat
scripts\load-test.cmd --users 300 --runs 3 --ramp 300 --warmup 300 --steady 1200 --report-month 2026-10
```

Сокращённый профиль полезен для измерения на локальном стенде с меньшим числом пользователей и записей. Его результаты относятся к указанному профилю. Для повторного испытания укажите новый путь `--output` внутри `.local` или оставьте автоматическое уникальное имя каталога.

```bat
scripts\load-test.cmd --users 60 --runs 3 --ramp 20 --warmup 20 --steady 60 --report-month 2026-10
```

Полный список параметров доступен через `scripts\load-test.cmd --help`. Времена заданы в секундах. `--seed` фиксирует порядок разгона и последовательности выбора действий. Для 300 пользователей выбираются 2 ADMIN, 60 OPERATOR, 40 ACCOUNTANT, 18 MANAGER и 180 CLIENT. В меньших профилях сохраняются пропорции с округлением и минимумом по одному пользователю каждой роли.

## Сценарии и фазы

Каждый виртуальный пользователь проходит HTTPS-вход с CSRF и хранит собственный защищённый `ACCOUNT_SESSION`. Перед завершением прогона выполняется выход. `readyBySteady` показывает число уникальных сеансов, созданных до стабильной фазы. `peakActiveUsers` показывает максимум одновременно активных пользователей генератора.

Обычные сценарии стремятся к пропорции HTTP-запросов 60% просмотр счетов и истории, 20% поиск, 10% финансовые действия и 10% выписки. Финансовый сценарий содержит четыре отдельных HTTP-запроса. Бухгалтер открывает форму, создаёт черновик, получает токен подтверждения и отправляет подтверждение. Начисления и платежи по 0,01 RUB выполняются на выделенных открытых счетах. Номера документов имеют префикс `E11-LOAD-<runId>-` и уникальный суффикс. Клиентские сеансы обращаются только к собственным счетам. Сотрудники читают выборку из максимум 512 синтетических счетов и выделенный счёт пользователя. Доля обращений к выделенному счёту при выборе цели чтения составляет примерно 20%. Пауза между обычными действиями составляет от одной до трёх секунд. Фактическая пропорция берётся из строк категории стабильного профиля.

Отдельная очередь выполняет CHARGES, PAYMENTS, DEBT и MOVEMENT с тем же месяцем. До пяти участников текущей нагрузки берут из очереди по одному отчёту. В очереди есть представители ADMIN, ACCOUNTANT и MANAGER. По умолчанию планируется 30 запросов каждого вида в каждом прогоне. `--reports-per-type` позволяет увеличить количество. Первая запланированная попытка каждого типа помечается `first-of-run`, её результат сохраняется отдельно от повторов. Состояние кэшей зависит от стенда и предыдущих запросов.

`RAMP`, `WARMUP` и `STEADY` записываются раздельно. Если к концу стабильной фазы остались отчётные запросы, те же участники могут закончить очередь в фазе `REPORT_TAIL`. Фаза ограничена `--report-tail`, по умолчанию 180 секундами. Остальные пользователи продолжают штатные действия в этом хвосте. В расчёт стабильного экранного p95 входят только запросы с меткой `STEADY`. Максимум по каждому отчёту учитывает все его замеры, включая первый запрос и хвост. Таймаут запроса задаётся `--timeout` и по умолчанию равен 60 секундам.

## Файлы результатов

| Файл | Содержание |
|---|---|
| `profile.properties` | URL, версия Java, число счетов и проведённых операций, месяц, seed, длительности и состав ролей |
| `run-NN/raw-results.jtl` | Реальные HTTP-запросы всех фаз, время в миллисекундах, код, признак успеха, размер тела, активные пользователи, категория, серия и `X-Request-ID` для сопоставления с логами |
| `run-NN/scenario-results.csv` | Результаты логических действий. Один успешный финансовый сценарий соответствует одному подтверждённому документу |
| `run-NN/summary.csv` | Число запросов, ошибки, HTTP 5xx, throughput, p50/p95/p99 и максимум по фазе, категории и маршруту |
| `run-NN/report-totals.csv` | Фактически отрисованные общие итоги каждого успешного отчёта по типу, порядковому номеру и колонке |
| `run-NN/run.properties` | Число сеансов, `runId`, число завершённых финансовых действий, незавершённые отчёты и показатели порогов |
| `run-NN/telemetry.csv` | Выборки CPU, RAM и диска, нагрузка Docker, активность PostgreSQL, ожидания блокировок и наблюдавшиеся долгие запросы |
| `run-NN/actuator-metrics.jsonl` | Выборки JVM heap и метрик Hikari через действующую сессию ADMIN, если метрики открыты в изолированном профиле |

Сырые HTTP-замеры содержат ошибки и таймауты. Запросы телеметрии помечаются отдельно. Для `STEADY:*` throughput равен числу запросов, делённому на заданное время стабильного измерения. Для остальных областей используется интервал от начала первого запроса до конца последнего. Процентили вычисляются по рангу `ceil(p × N)` без отбрасывания ошибок. `STEADY:screen` объединяет GET-страницы штатного профиля, включая формы бухгалтера. `STEADY:screen-route:*` выделяет каждый типовой GET. В `REPORT:route:*` проверяется максимум для четырёх типов, порог 10 секунд применяется к каждому запросу.

`--telemetry 15` задаёт интервал сбора данных в секундах. Значение 0 выключает сбор. При совместном размещении генератора и приложения оцените собственный CPU и heap генератора по `telemetry.csv`. PostgreSQL-выборки показывают наблюдавшиеся ожидания и длительности запросов. Таймер Hikari показывает агрегаты запросов на получение соединения. Недоступные метрики остаются в протоколе как `UNAVAILABLE`, `null` или ошибки категории `telemetry`.

Код возврата 0 означает завершённый профиль в рамках его выбранных параметров. Код 2 означает неполное число сеансов или отчётов, HTTP-ошибки, ошибку сценария либо выход за измеренный порог. При коде 2 файлы результатов сохраняются. Код 1 используется при отказе защиты стенда, конфигурационной ошибке и сбое самого генератора. Положительный результат сокращённого запуска подтверждает только измеренные параметры.

Перед нагрузкой и после неё выполните независимую сверку FIN-09 в изолированной базе. Для проверки числа проводок сопоставьте `successfulFinancialActions` из `run.properties` с фактическими POSTED по префиксу этого `runId`. Сопоставьте колонки `report-totals.csv` с независимым SQL для согласованного месяца. Протокол приёмки содержит фактические результаты, конфигурацию стенда, проверки прав и планов SQL.

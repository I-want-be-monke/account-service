# Сервис лицевых счетов клиентов — E1–E11

Приложение на Java 21, Spring Boot, PostgreSQL 17, Flyway, Spring Security и Spring Session JDBC. Работают вход, управление пользователями, журнал действий, клиенты, счета, начисления, платежи, исправления, история, кабинет клиента, выписки и сводные отчёты. E10 добавляет полный Compose-запуск, проверяемые резервные копии, учебное восстановление и атомарный импорт CSV-пакета.

## Требования

- Windows CMD, JDK **21** (`java -version`), Docker Desktop с Linux Engine (`docker info`), свободные порты 55432, 8080, 8443.
- Интернет при первой сборке для Maven 3.9.11 и зависимостей. Maven скачивается локальным Wrapper и проверяется по SHA-512.
- `JAVA_HOME` должен указывать на JDK 21. Например, в текущем CMD: `set "JAVA_HOME=C:\Program Files\Eclipse Adoptium\jdk-21"` и `set "PATH=%JAVA_HOME%\bin;%PATH%"` (подставьте свой фактический путь).

Если `docker info` в обычном CMD возвращает `Access is denied`, откройте Docker Desktop и убедитесь, что используется Linux Engine. Проверьте `whoami /groups | findstr /i docker-users`. Если пользователь не состоит в группе, администратор Windows может добавить его в `docker-users`, после чего нужно выйти из учетной записи Windows и войти снова. Ограниченный терминал внутри ассистента может показывать эту группу как `Deny only` даже при ее наличии у обычного пользовательского сеанса.

## Первый и повторный запуск

Откройте CMD:

```bat
cd /d C:\vyz\incheneria\account-service
scripts\dev-up.cmd
```

Скрипт при первом запуске создает `.env` со случайными паролями и `.local\dev.p12` с самоподписанным сертификатом, поднимает PostgreSQL, собирает JAR и запускает приложение. При повторном запуске использует прежние секреты и тот же Docker volume. **Не копируйте пустой `.env.example` поверх созданного `.env`.** Не удаляйте `.env`, пока используете существующую БД: пароли БД и хэши учебных пользователей сохраняются.

Откройте `https://localhost:8443/login`. Подтвердите исключение для локального самоподписанного сертификата только в этой учебной среде. Логины: `demo-admin`, `demo-operator`, `demo-accountant`, `demo-manager`, `demo-client`. Соответствующие пароли находятся в локальном `.env` в переменных `DEMO_ADMIN_PASSWORD` и т. д. Файл исключен из Git. Запускайте профиль `dev` только на своей машине; у него есть предсказуемые логины.

Остановка в CMD:

```bat
scripts\dev-down.cmd
```

Она останавливает приложение и PostgreSQL, **не удаляя volume с данными**. Повторный `dev-up.cmd` поднимает их снова. Логи приложения — `.local\logs\stdout.log`, `.local\logs\stderr.log` и `.local\logs\account-service.log`.

## Развёртывание, резервирование и перенос E10

Для полного Compose-запуска из CMD остановите режим JAR через `scripts\dev-down.cmd` и выполните `scripts\full-up.cmd`. Остановите полный профиль через `scripts\full-down.cmd`. Оба режима по умолчанию используют тот же том и адрес HTTPS. [Запуск, порты, настройки и логи](docs/deployment.md)

```bat
scripts\backup.cmd
scripts\backup-task.cmd status
scripts\restore-test.cmd
```

Копии хранятся в `.local\backups`. Проверочное восстановление открывается отдельно на `https://localhost:18443/login`. Выполните вход, проверьте журнал, выписку и отчёт, затем остановите проверочный экземпляр через `scripts\restore-test-down.cmd`. [Регистрация ежедневной задачи и восстановление на другом ПК](docs/backup.md)

Учебный импорт использует `migration\demo-package` и отдельную базу с собственными портом и файлом настроек. Сначала выполните `scripts\import-data.cmd dry-run`, затем `apply` с теми же аргументами. [Контракт CSV и команды](docs/import-format.md) · [Сценарий демонстрации](docs/admin-guide.md)

```bat

```

`test` запускает модульные проверки BCrypt, подтверждения, денежных правил и ошибки JDBC-сеанса. `verify` также запускает интеграционные проверки E1–E11 на PostgreSQL Testcontainers. ## Управление пользователями и журнал (E2)

Войдите как `demo-admin`. На главной откройте **Пользователи** (`/admin/users`). Доступны поиск по логину, роли и статусу, создание и редактирование имени/логина. Для смены роли, связи клиента или блокировки сначала выберите новое состояние и причину, затем откройте страницу проверки `/admin/users/{id}/confirm` и подтвердите действие. Подтверждение привязано к текущему администратору, версии записи и короткому серверному токену; оно действует десять минут и используется один раз. Прямой POST без него и CSRF отклоняется. Смена доступа отзывает сеансы пользователя.

Роль CLIENT требует ID существующей активной карточки клиента. Для учебной проверки откройте `demo-client` в списке пользователей: его ID клиента показан на странице редактирования. Карточки клиентов создаёт оператор в разделе «Клиенты»; создание пользователя не создаёт карточку автоматически.

На `/audit` администратор видит журнал, включая безопасность. Руководитель видит только разрешенные категории действий и доступа; входы и изменения прав ему не раскрываются. Оператор, бухгалтер и клиент не могут открыть журнал или административный интерфейс. Пароли и токены в события аудита не включаются.

Для отдельной среды без профиля `dev` первый администратор создается только на пустой БД при наличии внешней переменной `BOOTSTRAP_ADMIN_PASSWORD` (12–128 символов). Его логин — `bootstrap-admin`. После первого запуска удалите переменную из окружения. Демоучетные записи создаются только с профилем `dev`.

### Ручная проверка E2

1. Войдите как `demo-admin`, создайте пользователя `check-operator` с ролью «Оператор» и новым паролем длиной не менее 12 символов. Найдите его в списке. Повтор того же логина должен показать ошибку, не создавая вторую запись.
2. Войдите в другом окне браузера как `check-operator`. Прямой переход на `/admin/users` и `/audit` должен вернуть 403. В первом окне измените роль пользователя на «Бухгалтер-расчетчик»: до нажатия подтверждения роль в списке остается прежней; после подтверждения старый сеанс теряет доступ, а новый вход показывает новую роль.
3. Заблокируйте пользователя. Его открытый сеанс перестает работать и новый вход отклоняется. Разблокируйте и войдите заново. Попробуйте заблокировать единственного администратора: приложение должно отказать.
4. Проверьте `/audit`: создание, смена роли, блокировка, входы и отказы присутствуют с автором, временем, объектом и результатом. Под `demo-manager` журнал не должен раскрывать события безопасности. Проверьте, что паролей в деталях нет.
5. Выполните `mvnw.cmd clean verify` после остановки приложения и убедитесь в `BUILD SUCCESS`. Затем снова запустите приложение и проверьте, что созданный пользователь и журнал сохранились.

## Клиенты (E3)

Оператор открывает «Клиенты» (/clients), создаёт физическое лицо или организацию (/clients/new), меняет карточку и после отдельного подтверждения переводит её в архив либо возвращает из архива. Статус меняется только после выбора причины и подтверждения на сервере. Идентификатор уникален в пределах типа клиента и типа идентификатора, пробелы и регистр при сравнении нормализуются. Имя, тип, идентификатор, статус и контакты проверяет сервер. Поиск по номеру счёта и запрет архивирования клиента, пока есть незакрытые счета, работают с E4.

Администратор, бухгалтер и руководитель видят список и карточку, но не меняют клиента. Клиент не видит общий реестр и открывает только свою карточку по /me/client; принадлежность определяется по его учётной записи в БД. Изменения карточки и статуса записываются в аудит вместе с самой операцией.

### Ручная проверка E3

1. После запуска войдите как demo-operator. На /clients/new создайте PERSON с типом идентификатора DEMO и значением DEMO-P-0001, затем ORGANIZATION со значением DEMO-O-0001 (укажите разные имена и корректные контакты). Карточки появятся в списке и найдутся по имени, типу, идентификатору и статусу.
2. Попробуйте второй раз создать PERSON с DEMO-P-0001 в другом регистре и с пробелами: сервер должен отказать; список не пополнится. Неверный email также отклоняется.
3. Откройте карточку, отредактируйте контакты, затем смените статус через «Изменить статус» → «Продолжить» → «Подтвердить». До подтверждения статус не меняется. Посмотрите события CLIENT_CREATED, CLIENT_UPDATED, CLIENT_STATUS_CHANGED на /audit под администратором или руководителем.
4. Войдите как demo-accountant: список доступен, /clients/new и редактирование недоступны. Под demo-client доступна /me/client, а /clients и чужой UUID возвращают 403.
5. Остановите и запустите приложение заново: созданные карточки должны сохраниться. Для автоматической проверки выполните в CMD mvnw.cmd clean verify после scripts\dev-down.cmd.

## Лицевые счета (E4)

Оператор открывает карточку активного клиента на /clients и выбирает «Открыть счет» (/clients/{id}/accounts/new). Укажите дату не позже сегодняшней и отправьте форму. Сервер выделит постоянный номер вида LS-XXXXXXXXXX и создаст счет OPEN с нулевым сальдо в RUB. Повтор того же запроса открытия с тем же идентификатором формы возвращает прежний счет и не создает второй; следующий счет того же клиента получит новый номер. Номера глобально уникальны, возможны пропуски после отката транзакции.

На /accounts сотрудники ищут счета по номеру, статусу и ID клиента; у карточки /accounts/{id} показана история статусов. Оператор на /accounts/{id}/status указывает цель и причину, затем на отдельной странице /accounts/{id}/confirm подтверждает смену. Допустимы OPEN ↔ SUSPENDED и переход из OPEN/SUSPENDED в CLOSED при нулевом сальдо; CLOSED окончателен. Подтверждение одноразовое, привязано к версии счета и действует десять минут. Архивировать клиента, пока у него есть хотя бы один счет OPEN или SUSPENDED, нельзя. Поиск клиентов на /clients также принимает номер счета.

CLIENT открывает /my/accounts и только свою карточку счета; запрос чужого ID возвращает 403. ADMIN, ACCOUNTANT и MANAGER читают счета, но не открывают и не меняют их. Обязательный аудит открытия и смены статуса записывается атомарно с изменением и историей. Записи вносятся через формы с CSRF. С E5 закрытие счета также запрещено при наличии непроведенного черновика; черновик нужно провести либо отдельно отбросить.

### Ручная проверка E4

1. Запустите scripts\dev-up.cmd и войдите под demo-operator. На /clients откройте активного клиента, создайте ему два счета. Убедитесь, что номера различны и оба счета имеют сальдо 0,00 RUB.
2. На /accounts найдите счет по полному номеру, затем найдите клиента по номеру счета на /clients. Попробуйте отправить страницу открытия счета с будущей датой: появится ошибка, счет не создастся.
3. В карточке первого счета выберите SUSPENDED и причину. До отдельного подтверждения счет остается OPEN. Подтвердите, затем верните OPEN и переведите в CLOSED. Проверьте три записи в истории; закрытый счет нельзя снова открыть.
4. Пока второй счет OPEN, попытка архивировать клиента должна быть отклонена. Закройте второй счет и повторите архивирование; после подтверждения клиент станет ARCHIVED. Новые счета архивному клиенту не открываются.
5. В другом сеансе войдите как demo-client: /my/accounts показывает только его счета, чужой ID счета недоступен. Под demo-accountant /accounts читается, а /clients/{id}/accounts/new и POST смены статуса запрещены. Под администратором /audit содержит ACCOUNT_OPENED и ACCOUNT_STATUS_CHANGED.
6. Выполните scripts\dev-down.cmd, затем mvnw.cmd clean verify и mvnw.cmd test. После scripts\dev-up.cmd счета, их история и прежние карточки должны сохраниться.

## Начисления и платежи (E5)

Новый раздел на карточке счета /accounts/{id} ведет к движениям /accounts/{id}/operations. Бухгалтер создает начисление или регистрирует платеж на открытом счете через /accounts/{id}/operations/new. У начисления обязательны сумма, дата учета, расчетный месяц (первое число) и основание; номер документа можно добавить. Для платежа обязательны сумма, дата, основание, номер документа и один из учебных способов регистрации. Источник ручного документа назначается сервером — MANUAL. Реальные деньги сервис не принимает.

После сохранения появляется PREPARED: сальдо не меняется. Черновик можно изменить с проверкой версии либо отбросить после отдельного подтверждения. Для проведения откройте черновик, нажмите «Проверить и провести», просмотрите реквизиты и подтвердите; только после успешного commit он становится POSTED, сальдо и аудит изменяются вместе. Повтор одного подтверждения возвращает прежний результат без второй проводки. Положительное сальдо — долг; отрицательное — аванс. На SUSPENDED и CLOSED ничего провести нельзя; закрытие счета с PREPARED запрещено. Проведенная строка неизменяема. Исправления проведенных сумм описаны в разделе E6 ниже.

### Ручная проверка E5

1. Войдите как demo-operator, создайте тестовому активному клиенту новый OPEN счет. Запишите его номер и UUID из адреса. Для контроля удобно использовать отдельную синтетическую карточку клиента.
2. Войдите как demo-accountant, откройте карточку счета и выберите «Начислить». Укажите 1000,00, дату сегодня, расчетный месяц первым числом текущего месяца, основание и уникальный номер документа. Сохраните черновик: сальдо останется 0,00. На странице проверки подтвердите проведение: сальдо станет 1000,00.
3. Зарегистрируйте платеж 400,00 с другим уникальным номером документа и способом «Ручной перевод». После проведения сальдо станет 600,00. Повторная отправка той же страницы подтверждения не должна дать второй платеж. Новый черновик с уже использованным номером платежа должен получить отказ.
4. Создайте еще один черновик и попробуйте закрыть счет под demo-operator: сервер откажет, даже если сальдо было бы нулевым. Отбросьте черновик через страницу подтверждения; проверьте событие в аудите. На приостановленном счете новый черновик и проведение недоступны.
5. Под demo-admin и demo-operator страница создания операции недоступна; POST без CSRF отклоняется. Под demo-client свой счет и проведенные движения доступны, чужие операции и черновики недоступны.
6. Войдите как demo-admin на /audit: найдите OPERATION_PREPARED и OPERATION_POSTED, проверьте автора, объект и результат без паролей и ключей сеанса. После scripts\dev-down.cmd и scripts\dev-up.cmd записи и сальдо сохраняются.

Проверка сальдо в PostgreSQL из CMD после запуска:

```bat
docker compose --env-file .env exec db psql -U account_owner -d accounts -c "select a.account_number, a.current_balance, a.opening_balance + coalesce(sum(o.delta) filter (where o.storage_status='POSTED'),0) as calculated from personal_account a left join financial_operation o on o.account_id=a.id group by a.id, a.account_number, a.current_balance, a.opening_balance order by a.account_number"
```

## Исправления проведенных операций (E6)

Бухгалтер открывает проведенное начисление или платеж в списке движений счета и выбирает «Создать исправление» на /operations/{id}/corrections/new. Он указывает **целевую сумму** (включая 0 для аннулирования), причину и основание. Новая сумма сравнивается с эффектом исходной операции и всех ее проведенных исправлений. Сохраняется отдельный черновик CORRECTION; исходная дата, сумма и номер документа не меняются. Черновик можно отредактировать или отбросить. Для проведения нужна отдельная страница проверки, серверное подтверждение и CSRF.

Повторные исправления привязаны к исходной операции. Например, начисление 1000 → 900 → 800 дает два движения по −100. Платеж 400 → 350 дает движение +50. В карточке исходной операции отображаются все проведенные исправления и вычисляемое состояние «Исправлено». Проведение изменяет сальдо, строку исправления и обязательный аудит одной транзакцией. Устаревший черновик после другого проведенного исправления получает конфликт: подготовьте новый. Оператор, руководитель и клиент видят доступные им проведенные движения; выполнять исправления может только бухгалтер.

### Ручная проверка E6

1. Остановите приложение штатно: `scripts\dev-down.cmd`. Выполните `mvnw.cmd test` и `mvnw.cmd clean verify` (интеграционные тесты используют PostgreSQL Testcontainers), затем `scripts\dev-up.cmd`. Данные в Docker volume сохраняются.
2. В браузере https://localhost:8443/login войдите как demo-operator и создайте активному тестовому клиенту новый OPEN счет. Под demo-accountant проведите начисление 1000 и платеж 400 с разными номерами документов: сальдо 600.
3. Откройте начисление, создайте исправление с целью 900 и причиной. До проведения сальдо 600. На странице «Проверить и провести» подтвердите: сальдо 500, исходная сумма остается 1000, состояние «Исправлено».
4. Исправьте платеж 400 до 350: сальдо 550. Повторное исправление исходного начисления до 800 дает сальдо 450. Все три строки исправлений доступны из исходных операций, их эффекты −100, +50 и −100.
5. Попробуйте повторить текущую целевую сумму, ввести отрицательное число или пустую причину: отказ без изменения сальдо. Подготовьте два исправления одной исходной операции, проведите первое и попробуйте провести второе: сервер потребует новый черновик. Под demo-operator и demo-admin форма исправления недоступна; POST без CSRF отклоняется.
6. В /audit под demo-admin проверьте OPERATION_CORRECTION_PREPARED и OPERATION_CORRECTION_POSTED, исходный ID, цель и причину без секретов. Остановите и снова запустите приложение: сальдо и история сохраняются. SQL для сверки сохраненного и вычисленного сальдо приведен выше.

## История и кабинет клиента (E7)

На `/my/accounts` клиент видит все свои счета, включая закрытые; каждый счет ведет к карточке и истории. На `/accounts/{id}/operations` проведенные движения фильтруются по датам (включительно) и виду CHARGE/PAYMENT/CORRECTION. Размер страницы — 20, 50 или 100 в форме; сервер допускает от 1 до 100. Порядок: дата учета, время проведения и UUID по убыванию. Исправления ссылаются на исходную операцию, в карточке исходной записи видна вся цепочка. Черновики доступны только создавшему их бухгалтеру и не входят в историю. Полное сальдо счета не меняется при выборе фильтра.

Два JSON-маршрута чтения используют тот же HTTPS-сеанс: `/api/v1/accounts/{id}` и `/api/v1/accounts/{id}/operations?from=&to=&kind=&page=&size=`. Первый доступен всем ролям с правом чтения счета; финансовая история не доступна ADMIN. CLIENT получает только свои счета и движения. Поля и ошибки описаны в [docs/api.md](docs/api.md).

### Ручная проверка E7 через CMD и браузер

1. В CMD перейдите в проект: `cd /d C:\vyz\incheneria\account-service`. Для полной проверки остановите приложение `scripts\dev-down.cmd`, затем выполните `mvnw.cmd test` и `mvnw.cmd clean verify`. Запустите его вновь: `scripts\dev-up.cmd`. Штатная остановка сохраняет Docker volume.
2. Войдите на https://localhost:8443/login как `demo-client` (пароль из локального `.env`). Откройте «Мои счета», затем один из своих счетов и «История». Если своих счетов пока нет, создайте их для привязанной к `demo-client` карточки под `demo-operator`. Выберите вид «Исправления», укажите даты и убедитесь, что строки изменились, а полное сальдо счета осталось тем же. Нажмите «Сбросить», затем перейдите по ссылке исходной операции и обратно. Для готового примера с исправлениями сотрудник может открыть сохраненный тестовый счет LS-0000000004: после E6 на нем 550,00 ₽, если данные еще не менялись.
3. В той же сессии откройте `https://localhost:8443/api/v1/accounts/{id}` и `https://localhost:8443/api/v1/accounts/{id}/operations?kind=CORRECTION&size=1`, заменив `{id}` на UUID **своего** счета из адресной строки. JSON показывает строки сумм и пагинацию. Некорректная дата, вид или размер страницы дают 400 с `code` и `requestId`.
4. Для проверки изоляции создайте под `demo-operator` второго клиента и счет, а под `demo-admin` отдельную учетную запись CLIENT, связанную с этой карточкой. Войдите первым клиентом и подставьте UUID чужих клиента, счета и операции в адреса карточки, истории и API: получите 403 без чужих реквизитов. Под вторым клиентом доступен его счет, но не первый. Под `demo-accountant` черновики видны только их автору.

## Безопасность и границы

`.env`, сертификат, кеш Wrapper, сборка и логи исключены из Git. Пароли хранятся в БД только как BCrypt-хэши. В dev TLS самоподписан; рабочий сертификат и внешний секрет нужны при развертывании. Профиль без `dev` создаёт первого администратора только с переданным паролем `BOOTSTRAP_ADMIN_PASSWORD` на пустой БД. Счета открываются с нулевым сальдо в RUB; начисления и платежи изменяют его только при проведении. Закрытие требует нулевого сальдо и отсутствия черновиков. Исправления выполнены в E6, выписки в E8, сводные отчёты в E9. Состояние этапа и фактические проверки — в `docs\project-status.md`.

## Выписка по лицевому счёту (E8)

Откройте карточку счёта и ссылку «Сформировать выписку», выберите начальную и конечную даты, нажмите «Сформировать выписку». Обе даты обязательны, включаются в период; допускается не более 366 календарных дней, начиная не раньше доступной истории счёта. Пустой период тоже даёт документ: обороты нулевые, входящее и исходящее сальдо совпадают. Приостановленные и закрытые счета доступны для разрешённого чтения.

Документ показывает UUID и номер счёта, владельца, период, время формирования, RUB, входящее сальдо, все проведённые движения, обороты увеличения и уменьшения задолженности и исходящее сальдо. Каждое исправление содержит ссылку на исходную операцию. Положительное сальдо — долг, отрицательное — переплата. Входящее = начальное сальдо счёта + сумма проведённых delta строго до периода; исходящее = входящее + увеличение − уменьшение. Текущее сальдо счёта не подменяет исторический остаток.

Кнопки документа позволяют изменить период, открыть печатное представление, скачать CSV или получить JSON. Все форматы рассчитывает один сервис из согласованного снимка PostgreSQL. Отдельные запросы могут увидеть новое проведение между скачиваниями — сравнивайте форматы при неизменных данных.

Выписки доступны ADMIN, OPERATOR, ACCOUNTANT, MANAGER и владельцу CLIENT. ADMIN читает финансовые движения в выписке, при этом отдельный маршрут истории E7 для него по-прежнему закрыт. CLIENT открывает только собственные счета; подмена UUID в HTML, печати, CSV или JSON возвращает 403. Контракт форматов и адреса — в [docs/api.md](docs/api.md); пошаговая инструкция по ролям — в [docs/user-guide.md](docs/user-guide.md).

## Сводные финансовые отчёты E9

Войдите как администратор, бухгалтер или руководитель и откройте «Финансовые отчёты». Выберите месяц начислений или платежей, дату задолженности либо период движения. При необходимости укажите UUID клиента и текущий статус счёта.

Все подходящие счета участвуют в итогах. Страницы меняют состав показанных строк. Номер счёта открывает его карточку. Печатное представление содержит текущую страницу и общий итог. CSV содержит полную выборку. JSON возвращает запрошенную страницу и общие итоги.

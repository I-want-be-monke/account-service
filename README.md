# Сервис лицевых счетов клиентов

Сервис на Java 21, Spring Boot, PostgreSQL 17, Flyway, Spring Security и Spring Session JDBC для ведения клиентов, лицевых счетов, начислений, платежей, исправлений, истории операций, выписок и сводных финансовых отчётов.

Поддерживаются вход и управление пользователями, журнал действий, клиенты, счета, начисления, платежи, исправления проведённых операций, история, кабинет клиента, выписки и сводные отчёты. Дополнительно реализованы полный Compose-запуск, проверяемые резервные копии, учебное восстановление и атомарный импорт CSV-пакета.

## Стек

- Java 21
- Spring Boot
- PostgreSQL 17
- Flyway
- Spring Security
- Spring Session JDBC
- Docker Compose
- Локальные компоненты Tabler 1.7.5

## Требования

- Windows CMD
- JDK 21, проверка: `java -version`
- Docker Desktop с Linux Engine, проверка: `docker info`
- Свободные порты: `55432`, `8080`, `8443`
- Интернет при первой сборке для Maven 3.9.11 и зависимостей
- Maven скачивается локальным Wrapper и проверяется по SHA-512

`JAVA_HOME` должен указывать на JDK 21. Например, в текущем CMD:

```bat
set "JAVA_HOME=C:\Program Files\Eclipse Adoptium\jdk-21"
set "PATH=%JAVA_HOME%\bin;%PATH%"
```

Подставьте фактический путь к JDK.

Если `docker info` в обычном CMD возвращает `Access is denied`, откройте Docker Desktop и убедитесь, что используется Linux Engine. Проверьте:

```bat
whoami /groups | findstr /i docker-users
```

Если пользователь не состоит в группе `docker-users`, администратор Windows может добавить его в группу, после чего нужно выйти из учётной записи Windows и войти снова.

## Локальный запуск

Откройте CMD:

```bat
cd /d C:\vyz\incheneria\account-service
scripts\dev-up.cmd
```

При первом запуске скрипт:

- создаёт `.env` со случайными паролями;
- создаёт `.local\dev.p12` с самоподписанным сертификатом;
- поднимает PostgreSQL;
- собирает JAR;
- запускает приложение.

При повторном запуске используются прежние секреты и тот же Docker volume.

Не копируйте пустой `.env.example` поверх созданного `.env`. Не удаляйте `.env`, пока используете существующую БД: пароли БД и хэши учебных пользователей сохраняются.

Откройте:

```text
https://localhost:8443/login
```

Подтвердите исключение для локального самоподписанного сертификата только в этой учебной среде.

Логины профиля `dev`: `demo-admin`, `demo-operator`, `demo-accountant`, `demo-manager`, `demo-client`. Пароли находятся в локальном `.env` в переменных `DEMO_ADMIN_PASSWORD` и т. д. Файл исключён из Git. Профиль `dev` предназначен только для локальной машины.

Остановка:

```bat
scripts\dev-down.cmd
```

Команда останавливает приложение и PostgreSQL, не удаляя volume с данными. Повторный `dev-up.cmd` поднимает их снова.

Логи приложения:

```text
.local\logs\stdout.log
.local\logs\stderr.log
.local\logs\account-service.log
```

## Полный Compose-запуск, резервирование и импорт

Для полного Compose-запуска остановите режим JAR и выполните:

```bat
scripts\dev-down.cmd
scripts\full-up.cmd
```

Остановка полного профиля:

```bat
scripts\full-down.cmd
```

Оба режима по умолчанию используют тот же том и адрес HTTPS.

Резервное копирование и проверочное восстановление:

```bat
scripts\backup.cmd
scripts\backup-task.cmd status
scripts\restore-test.cmd
```

Копии хранятся в `.local\backups`. Проверочное восстановление открывается отдельно:

```text
https://localhost:18443/login
```

После проверки журнала, выписки и отчёта остановите проверочный экземпляр:

```bat
scripts\restore-test-down.cmd
```

Учебный импорт использует тестовый CSV-пакет и отдельную базу с собственными портом и файлом настроек. Сначала выполните `dry-run`, затем `apply` с теми же аргументами:

```bat
scripts\import-data.cmd dry-run
scripts\import-data.cmd apply
```

## Сборка и тесты

При запущенном Docker Desktop:

```bat
mvnw.cmd test
mvnw.cmd verify
```

`test` запускает модульные проверки BCrypt, подтверждений, денежных правил и ошибки JDBC-сеанса.

`verify` дополнительно запускает интеграционные проверки на PostgreSQL Testcontainers:

- `MigrationImportIT` проверяет dry-run, атомарность, происхождение, сверку и повторы импорта;
- `BackupRestoreIT` проверяет архив PostgreSQL, восстановление, обновление схемы, вход, выписку и отчёт.

Временные тестовые БД и рабочая БД публикуют порт на `127.0.0.1`.

Результаты тестов находятся в:

```text
target\surefire-reports
target\failsafe-reports
```

Для сборки приложения без тестов:

```bat
mvnw.cmd -DskipTests package
```

Перед `mvnw.cmd clean verify` остановите запущенное приложение:

```bat
scripts\dev-down.cmd
```

Windows не удаляет используемый JAR. Затем выполните:

```bat
mvnw.cmd clean verify
scripts\dev-up.cmd
```

Остановка не удаляет данные БД.

## Функциональность

### Пользователи и журнал действий

Администратор открывает раздел **Пользователи** (`/admin/users`). Доступны поиск по логину, роли и статусу, создание и редактирование имени/логина.

Для смены роли, связи клиента или блокировки сначала выбирается новое состояние и причина, затем открывается страница проверки `/admin/users/{id}/confirm` и подтверждается действие. Подтверждение привязано к текущему администратору, версии записи и короткому серверному токену. Оно действует десять минут и используется один раз. Прямой POST без подтверждения и CSRF отклоняется. Смена доступа отзывает сеансы пользователя.

Роль `CLIENT` требует связи с существующей активной карточкой клиента. В форме пользователя клиент выбирается по имени или названию. Карточки клиентов создаёт оператор в разделе «Клиенты». Создание пользователя и создание карточки клиента выполняются отдельно.

На `/audit` администратор видит журнал, включая события безопасности. Руководитель видит только разрешённые категории действий и доступа; входы и изменения прав ему не раскрываются. Оператор, бухгалтер и клиент не могут открыть журнал или административный интерфейс. Пароли и токены в события аудита не включаются.

Для отдельной среды без профиля `dev` первый администратор создаётся только на пустой БД при наличии внешней переменной `BOOTSTRAP_ADMIN_PASSWORD` длиной 12–128 символов. Его логин — `bootstrap-admin`. После первого запуска переменную нужно удалить из окружения. Демоучётные записи создаются только с профилем `dev`.

### Клиенты

Оператор открывает «Клиенты» (`/clients`), создаёт физическое лицо или организацию (`/clients/new`), меняет карточку и после отдельного подтверждения переводит её в архив либо возвращает из архива.

Статус меняется только после выбора причины и подтверждения на сервере. Идентификатор уникален в пределах типа клиента и типа идентификатора; пробелы и регистр при сравнении нормализуются. Имя, тип, идентификатор, статус и контакты проверяются сервером. Поиск по номеру счёта и запрет архивирования клиента, пока есть незакрытые счета, работают вместе с лицевыми счетами.

Администратор, бухгалтер и руководитель видят список и карточку, но не меняют клиента. Клиент не видит общий реестр и открывает только свою карточку по `/me/client`; принадлежность определяется по его учётной записи в БД. Изменения карточки и статуса записываются в аудит вместе с самой операцией.

### Лицевые счета

Оператор открывает карточку активного клиента на `/clients` и выбирает «Открыть счет» (`/clients/{id}/accounts/new`). Дата указывается не позже сегодняшней. Сервер выделяет постоянный номер вида `LS-XXXXXXXXXX` и создаёт счёт `OPEN` с нулевым сальдо в RUB.

Повтор того же запроса открытия с тем же идентификатором формы возвращает прежний счёт и не создаёт второй. Следующий счёт того же клиента получит новый номер. Номера глобально уникальны; возможны пропуски после отката транзакции.

На `/accounts` сотрудники ищут счета по номеру, статусу и ID клиента. В карточке `/accounts/{id}` показана история статусов. Оператор на `/accounts/{id}/status` указывает цель и причину, затем на `/accounts/{id}/confirm` подтверждает смену.

Допустимы переходы `OPEN ↔ SUSPENDED` и переход из `OPEN`/`SUSPENDED` в `CLOSED` при нулевом сальдо. `CLOSED` окончателен. Подтверждение одноразовое, привязано к версии счёта и действует десять минут.

Архивировать клиента, пока у него есть хотя бы один счёт `OPEN` или `SUSPENDED`, нельзя. Поиск клиентов на `/clients` также принимает номер счёта.

`CLIENT` открывает `/my/accounts` и только свою карточку счёта; запрос чужого ID возвращает 403. `ADMIN`, `ACCOUNTANT` и `MANAGER` читают счета, но не открывают и не меняют их. Обязательный аудит открытия и смены статуса записывается атомарно с изменением и историей. Записи вносятся через формы с CSRF. Закрытие счёта запрещено при наличии непроведённого черновика; черновик нужно провести либо отдельно отбросить.

### Начисления и платежи

На карточке счёта `/accounts/{id}` раздел движений ведёт к `/accounts/{id}/operations`. Бухгалтер создаёт начисление или регистрирует платёж на открытом счёте через `/accounts/{id}/operations/new`.

У начисления обязательны сумма, дата учёта, расчётный месяц (первое число) и основание; номер документа можно добавить. Для платежа обязательны сумма, дата, основание, номер документа и один из учебных способов регистрации. Источник ручного документа назначается сервером — `MANUAL`. Реальные деньги сервис не принимает.

После сохранения появляется `PREPARED`: сальдо не меняется. Черновик можно изменить с проверкой версии либо отбросить после отдельного подтверждения. Для проведения нужно открыть черновик, нажать «Проверить и провести», просмотреть реквизиты и подтвердить. Только после успешного commit операция становится `POSTED`, сальдо и аудит изменяются вместе. Повтор одного подтверждения возвращает прежний результат без второй проводки.

Положительное сальдо — долг; отрицательное — аванс. На `SUSPENDED` и `CLOSED` ничего провести нельзя. Закрытие счёта с `PREPARED` запрещено. Проведённая строка неизменяема.

### Исправления проведённых операций

Бухгалтер открывает проведённое начисление или платёж в списке движений счёта и выбирает «Создать исправление» на `/operations/{id}/corrections/new`.

Указывается целевая сумма, включая `0` для аннулирования, причина и основание. Новая сумма сравнивается с эффектом исходной операции и всех её проведённых исправлений. Сохраняется отдельный черновик `CORRECTION`; исходная дата, сумма и номер документа не меняются. Черновик можно отредактировать или отбросить. Для проведения нужна отдельная страница проверки, серверное подтверждение и CSRF.

Повторные исправления привязаны к исходной операции. Например, начисление `1000 → 900 → 800` даёт два движения по `−100`. Платёж `400 → 350` даёт движение `+50`. В карточке исходной операции отображаются все проведённые исправления и вычисляемое состояние «Исправлено». Проведение изменяет сальдо, строку исправления и обязательный аудит одной транзакцией. Устаревший черновик после другого проведённого исправления получает конфликт: нужно подготовить новый. Оператор, руководитель и клиент видят доступные им проведённые движения; выполнять исправления может только бухгалтер.

### История и кабинет клиента

На `/my/accounts` клиент видит все свои счета, включая закрытые; каждый счёт ведёт к карточке и истории.

На `/accounts/{id}/operations` проведённые движения фильтруются по датам включительно и виду `CHARGE`/`PAYMENT`/`CORRECTION`. Размер страницы — 20, 50 или 100 в форме; сервер допускает от 1 до 100. Порядок: дата учёта, время проведения и UUID по убыванию. Исправления ссылаются на исходную операцию, в карточке исходной записи видна вся цепочка. Черновики доступны только создавшему их бухгалтеру и не входят в историю. Полное сальдо счёта не меняется при выборе фильтра.

Два JSON-маршрута чтения используют тот же HTTPS-сеанс:

```text
/api/v1/accounts/{id}
/api/v1/accounts/{id}/operations?from=&to=&kind=&page=&size=
```

Первый доступен всем ролям с правом чтения счёта; финансовая история не доступна `ADMIN`. `CLIENT` получает только свои счета и движения. Поля и ошибки описаны в `docs/api.md`.

### Выписка по лицевому счёту

В карточке счёта откройте «Сформировать выписку», выберите начальную и конечную даты и нажмите «Сформировать выписку». Обе даты обязательны и включаются в период; допускается не более 366 календарных дней, начиная не раньше доступной истории счёта. Пустой период тоже даёт документ: обороты нулевые, входящее и исходящее сальдо совпадают. Приостановленные и закрытые счета доступны для разрешённого чтения.

Документ показывает номер счёта, владельца, период, время формирования, входящее сальдо, все проведённые движения, обороты увеличения и уменьшения задолженности и исходящее сальдо. Суммы отображаются в рублях с разделением тысяч и десятичной запятой. Технические реквизиты операции раскрываются отдельно. Положительное сальдо означает долг, отрицательное — переплату.

Входящее сальдо = начальное сальдо счёта + сумма проведённых delta строго до периода. Исходящее = входящее + увеличение − уменьшение. Текущее сальдо счёта не подменяет исторический остаток.

Кнопки документа позволяют изменить период, открыть печатное представление, скачать CSV или получить JSON. Все форматы рассчитывает один сервис из согласованного снимка PostgreSQL. Отдельные запросы могут увидеть новое проведение между скачиваниями — сравнивайте форматы при неизменных данных.

Выписки доступны `ADMIN`, `OPERATOR`, `ACCOUNTANT`, `MANAGER` и владельцу `CLIENT`. `ADMIN` читает финансовые движения в выписке, при этом отдельный маршрут истории для него по-прежнему закрыт. `CLIENT` открывает только собственные счета; подмена UUID в HTML, печати, CSV или JSON возвращает 403. Контракт форматов и адреса — в `docs/api.md`; пошаговая инструкция по ролям — в `docs/user-guide.md`.

### Сводные финансовые отчёты

Администратор, бухгалтер или руководитель открывает «Финансовые отчёты» в боковом меню. Переключатель предлагает начисления, платежи, задолженность и движение по счетам. Форма показывает только применимые к виду отчёта даты.

Чтобы ограничить данные одним клиентом, введите его имя или название и выберите результат. Сервер возвращает до 20 совпадений. Без JavaScript кнопка «Найти» открывает список с кнопками выбора. Пустое поле клиента включает всех доступных клиентов. При необходимости задайте текущий статус счёта и размер страницы.

Все подходящие счета участвуют в итогах. Страницы меняют состав показанных строк. Номер счёта открывает его карточку. Печатное представление содержит текущую страницу и общий итог. CSV содержит полную выборку. JSON возвращает запрошенную страницу и общие итоги.

## Безопасность и границы

`.env`, сертификат, кеш Wrapper, сборка и логи исключены из Git. Пароли хранятся в БД только как BCrypt-хэши. В `dev` TLS самоподписан; рабочий сертификат и внешний секрет нужны при развёртывании.

Профиль без `dev` создаёт первого администратора только с переданным паролем `BOOTSTRAP_ADMIN_PASSWORD` на пустой БД.

Счета открываются с нулевым сальдо в RUB. Начисления и платежи изменяют сальдо только при проведении. Закрытие требует нулевого сальдо и отсутствия черновиков. Исправления, выписки и сводные отчёты реализованы.

# E0: решения перед реализацией E1

Дата: 5 ноября 2026 года. Основа: `../../docs/system-design.md`, разделы 1–5, 8.3–8.4; исходные ЛР 3, 4, 5–6, 9–10 и методические указания в родительской папке.

## Проверка границ

- Модульный монолит с браузером, одним Spring Boot и PostgreSQL соответствует ЛР 3, табл. 6.2, ЛР 4, разд. 6–7, SR-01–03/13/18, и процессам A1–A5 ЛР 5–6. Роли пользователей не смешиваются с ролями проектной команды ЛР 9–10.
- E1 реализует только первый исполняемый срез: соединение, исходную схему идентификации, вход, выход и защищенную главную страницу. Требования к клиентам, счетам, операциям, отчетам и полноценному аудиту остаются в E2–E12 согласно матрице. Наличие таблиц `client` и `audit_event` в V1 не означает, что их пользовательские сценарии готовы.
- ЛР 7–8 отсутствуют в исходной папке. Это ограничение полноты моделей UML, но ни одна отсутствующая схема не нужна для входа, миграций и HTTPS в E1. Перед соответствующими этапами модели следует сверить дополнительно.

А-04 влияет на минимальную структуру клиента для обязательного FK роли CLIENT, А-07 — на уникальную связь клиента и пользователя, А-16 — на время и сеанс, А-17 — на будущую атомарность аудита (структура V1 готова), А-19 — на JDBC-сеансы. Остальные допущения A-01–03, 05–06, 08–15, 18, 20 не определяют поведение E1; они требуют отдельного решения перед E3–E10. Варианты из проектного документа не объявляются требованиями лабораторных.

## Согласование моделей и безопасности

`app_user.client_id` ссылается на `client` и может быть заполнен только для CLIENT; `app_role` фиксирован; `audit_event` не редактируется runtime; `spring_session*` — технические таблицы без JPA-моделей. Flyway создает схему до проверки JPA. Дополнительные таблицы счетов и финансовых операций не создаются в E1, поэтому нет преждевременного выбора денежных инвариантов.

Потенциальное несовпадение: `client.import_run_id` из проектной модели появится вместе с `import_run` в V5, когда будет реализован перенос; это добавочная миграция, не изменение V1. Требование аудита входов и отказов завершится в E2; E1 не заявляет его выполненным.

## Открытые решения

- E2: политика создания/сброса первоначального администратора вне dev; регистрация событий входа и отказа; отзыв всех сеансов после изменения роли.
- E3–E4: учебный идентификатор клиента и полный жизненный цикл счета (A-03–06).
- E5–E6: точность, знак сальдо, ключи документов и корректировки (A-01/02/09–13).
- E8–E10: периоды, перенос и резервное восстановление (A-14/15/18).

## Проверка доступности

В текущем терминале обнаружена Java 17; JDK 21 и Maven отсутствуют в PATH. Подключение к Docker Engine через named pipe отклонено. Доступ к Maven Central и Adoptium из терминала ограничен. Это препятствует фактической сборке и интеграционной приемке в этом окружении; совместимость версий проверена по документации, а не испытана локально.

## E2: решения по правам и аудиту

Дата: 5 ноября 2026 года. По сообщению пользователя, E1 запущен и протестирован в его обычном Windows-сеансе. Прежний абзац выше отражает только ограничения агентского терминала на E1.

- V1/V2 неизменны: уникальность логина, фиксированные роли, обязательная связь CLIENT, статусы и `auth_version` уже защищены CHECK/FK/UNIQUE. Новая миграция не нужна. В E2 разрешена только серверная запись в существующие `app_user`, `audit_event`, `spring_session`.
- Роль и статус меняются через POST подготовки и отдельную страницу подтверждения (проект §6.3–6.4, SR-26). В JDBC-сеансе хранится один pending-запрос с actorId, userId, версией, параметрами, причиной, случайным токеном и сроком 10 минут. POST подтверждения повторно проверяет версию и правила. CSRF остается включенным.
- При смене роли/статуса/привязки `auth_version` растет, строки сеансов удаляются по старому логину в той же транзакции. Каждый следующий защищенный запрос повторно проверяет роль, статус и версию в БД (проект §4.4). Переименование логина также отзывает сеансы.
- Запрещена блокировка себя и последнего активного ADMIN. Активные администраторы блокируются `SELECT ... FOR UPDATE` при опасном переходе для защиты от одновременного снятия прав.
- Успешное изменение пользователя и аудит разделяют одну транзакцию; отказ после отката пишется отдельным `REQUIRES_NEW`. Успешный вход журналируется до выдачи доступа, а сбой записи аудита отменяет сеанс (проект §4.9, BR-12/13). Неизвестный логин получает `actor_user_id=NULL`; в журнале нет пароля, хэша или токена.
- Администратор читает все категории журнала. Руководитель видит только BUSINESS/ACCESS; SECURITY управления входом и правами скрыт в сервисе, а не только в UI (проект §6.1, P22/P23).
- Первый администратор вне dev создается на пустой БД только при переданном внешнем пароле, с аудитом от SYSTEM. Профиль dev продолжает использовать прежние учебные записи и не меняет их пароли.
- Управление клиентскими карточками, финансовые команды и их объектные права остаются E3–E12. Создание CLIENT использует существующую активную карточку; тесты создают изолированную fixture.


## E3: карточки клиентов

Дата: 5 ноября 2026 года. Используется уже применённая миграция V1: таблица client, уникальный составной ключ, версия записи и статусы существуют с E1. Миграции V1/V2 не менялись; персональные данные для учебных тестов синтетические.

- Создавать и редактировать карточки, архивировать и восстанавливать может только OPERATOR. ADMIN, ACCOUNTANT и MANAGER читают общий реестр; CLIENT читает собственную карточку через привязку app_user.client_id. URL не принимает чужой UUID для роли CLIENT. Проверка прав происходит и на маршруте, и в сервисе.
- Нормализованный ключ идентификатора устраняет пробелы и учитывает регистр в сравнении. Для одного типа клиента и типа идентификатора дубль отклоняется и на уровне сервиса, и ограничением БД. Изменение проверяет version и фиксируется обязательным аудитом в той же транзакции.
- Смена статуса требует причины и двух POST/GET шагов с отдельным одноразовым подтверждением в JDBC-сеансе и CSRF. Подтверждение привязано к оператору, карточке, версии, статусу и сроку десять минут.
- Запрет архивации клиента с открытым счётом и поиск по номеру счёта включатся в E4 одновременно с появлением таблицы personal_account; без неё нельзя выполнить это условие или проверить такой сценарий. Остальные операции E4–E12 не создаются.
- Docker Engine доступен из доверенного пользовательского сеанса через Remote Desktop Commander и используется Testcontainers. У отдельного служебного терминала по-прежнему ограниченный Windows-токен с docker-users Deny only; ACL Docker Engine не менялся.

## E4: лицевые счета и конкурирующие изменения

Дата: 5 ноября 2026 года. Миграции V1/V2 не меняются; V3 добавляет счета, последовательность номеров и историю статусов. Постоянный номер выделяется только PostgreSQL sequence по формату LS-XXXXXXXXXX: пропуски при откате допустимы, повторное использование номера запрещено. Клиент, номер, дата открытия, начальное сальдо и валюта неизменны и защищены триггером. Баланс при открытии 0,00 RUB; денежные проводки остаются E5–E6.

- UUID, отправленный скрытым полем формы открытия, служит ключом повтора: повтор с тем же клиентом и датой возвращает ранее созданный счет без нового события аудита; повтор с другими реквизитами отклоняется. Операции открытия сначала блокируют строку клиента SELECT FOR UPDATE, затем проверяют наличие ключа и статус; архивирование клиента использует тот же замок и отклоняется, если счет OPEN или SUSPENDED. Это закрывает гонку открытия и архивации.
- Статус счета меняется только оператором через одноразовое подтверждение в серверном JDBC-сеансе с 10-минутным сроком, привязкой к автору, счету, статусу, причине и версии. Счет блокируется до повторной проверки перехода и записи истории. CLOSED окончателен и на уровне БД; переход в него требует нулевого сальдо. Признак даты используется по часовому поясу Europe/Moscow; открытие будущей датой запрещено.
- История статусов и обязательный бизнес-аудит записываются в одной транзакции со счетом. Если обязательный аудит не записан, вся операция откатывается. Отказы после отката идут отдельной попыткой аудита. ADMIN, ACCOUNTANT и MANAGER читают общие счета, OPERATOR открывает и меняет статусы, CLIENT читает только счета своей карточки (сервис проверяет принадлежность объекта).
- Таблицы финансовых документов и черновиков появятся на E5. При закрытии дополнительно потребуется проверка отсутствия незавершенных документов, тогда же текущий баланс будет вычисляться по проводкам. До E5 отсутствие таблицы делает такую проверку неприменимой. Проект не создаёт фиктивных финансовых операций.

## E5: начисления, платежи и проведение

Дата: 5 ноября 2026 года. Новая миграция V4 добавляет единую таблицу financial_operation для PREPARED и POSTED. Колонки и составной FK для CORRECTION уже определены по проекту, но формы/команды исправления появятся в E6. Ранее применённые V1–V3 не изменяются.

- Положительное сальдо означает долг клиента; CHARGE увеличивает долг, PAYMENT уменьшает, переплата допускает отрицательное сальдо. Деньги только RUB и BigDecimal/numeric(19,2): ввод с запятой либо точкой, не более двух дробных знаков, без скрытого округления. Начисление относится к первому числу месяца; дата учета не раньше доступной истории и не будущая.
- Бухгалтер создает, изменяет и по отдельному подтверждению отбрасывает только собственные PREPARED. Для создания/проведения и изменения сальдо нужен OPEN; отбрасывание разрешено на приостановленном счете, чтобы не оставлять неустранимый черновик. Закрытие счета под той же блокировкой запрещено, пока существует PREPARED.
- Источник ручного документа назначается сервером как MANUAL. Для PAYMENT обязательны способ MANUAL_TRANSFER/CASH_REGISTRATION и внешний номер. Для CHARGE номер необязателен. Нормализованный номер глобально уникален среди проведенных документов одного источника и вида, в том числе на разных счетах.
- Страница проведения связывает UUID намерения, версию черновика и SHA-256 канонического набора финансовых полей с бухгалтером и операцией в JDBC-сеансе на десять минут. Повтор того же подтверждения возвращает POSTED без нового эффекта; чужой токен, изменение черновика или повтор ключа с иным содержимым дает конфликт. При гонке разных счетов окончательную защиту документа обеспечивает индекс PostgreSQL.
- Общий порядок блокировки при проведении: счет → черновик; после повторной проверки выполняются POSTED → новое сальдо → обязательный аудит → commit. Для всех изменений черновика запись обязательного аудита входит в транзакцию. PostgreSQL trigger запрещает UPDATE/DELETE проведенной строки и прямую INSERT POSTED; операции чтения не выдают черновики клиенту. Отказы после rollback журналируются отдельным сервисом.
- Полная фильтрация истории по дате/типу, выписки и CSV остаются E7–E8; в E5 страница движений показывает проведенные записи и принадлежащие бухгалтеру черновики. Корректировки и их целевые суммы — E6. Никакого реального приема денег или интеграции с банком нет.

## E6: отдельные исправления и защита от устаревших черновиков

Дата: 5 ноября 2026 года. Исправление является новой записью CORRECTION, привязанной непосредственно к исходному POSTED CHARGE/PAYMENT того же счета. Исходная строка остается неизменной. Дата исправления — текущая дата по Europe/Moscow; учетная дата исходной строки не переписывается. Все последующие исправления ссылаются на исходную строку, а не друг на друга.

- Цель задает новый абсолютный эффект исходной операции: для CHARGE +target, для PAYMENT −target. Разность с текущим эффектом исходной записи и всех ее POSTED-исправлений записывается отдельным подписанным движением. Цель 0 допустима; нулевая разность не создает операцию. Видимое состояние CORRECTED вычисляется при чтении, в БД исходная строка продолжает хранить POSTED.
- Дополнительная последовательная миграция V5 добавляет счетчик POSTED-исправлений на момент подготовки черновика и проверяет его обязательность. При проведении сервис под замком счета сверяет этот счетчик и дельту с актуальными строками. PostgreSQL-триггер повторно проверяет исходную операцию, счетчик и формулу дельты; V1–V4 остаются неизменными. Даже если несколько последующих исправлений вернули прежнюю целевую сумму, старый черновик признается устаревшим. Плановую миграцию импорта придется нумеровать следующей свободной версией, а не V5.
- Подготовка, изменение, удаление черновика и проведение используют прежние серверные роли, подтверждение, idempotency key, CSRF и транзакционный аудит. Fingerprint дополнен ID исходной записи, целью, причиной и счетчиком исправлений. При недоступности обязательного аудита изменение и баланс откатываются. Отказ после отката записывается отдельно, когда запрос проходит через контроллер.
- Полный поиск истории, периоды, выписки и внешнее API остаются на E7–E9 по плану.

## E7: единое чтение счета и проведенной истории

Дата: 5 ноября 2026 года. Политика `AccountAccessPolicy` проверяет владельца CLIENT по текущей привязке пользователя в PostgreSQL и служит общей точкой доступа для карточки счета, HTML-истории и JSON. CLIENT получает только собственные счета, включая закрытые. Роль ADMIN читает реквизиты счета, но финансовая история через UI/API для нее закрыта по матрице.

- `HistoryQueryService` выбирает только POSTED SQL-проекцией с параметризованными фильтрами и ограниченными страницами. Порядок `operation_date DESC, posted_at DESC, id DESC` устраняет неоднозначность в стабильном наборе данных. `CORRECTED` вычисляется через индекс исправлений, исходная строка не меняется. Для пары count/rows одного запроса используется read-only REPEATABLE READ; разные HTTP-страницы при параллельном проведении не обещают общего снимка. Сальдо показывается полным из счета, независимо от фильтра.
- Отдельные DTO `OperationView` и JSON-проекции не раскрывают пароли, роли сотрудников, внутренние ключи, версии и ID автора проведения. API E7 ограничен двумя GET: счет и страница проведенных движений. HTTPS-сеанс и отзыв прав остаются прежними; ошибки API возвращают `application/problem+json` с `code` и `requestId`. Изменяющий финансовый API не добавлен.
- Схема V1–V5 достаточна: миграция E7 не нужна, данные и Docker volume сохраняются. Выписка с согласованным расчетом исторических остатков, CSV и отчеты относятся к E8–E9.

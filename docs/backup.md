# Резервное копирование и проверка восстановления

## Ручная копия

В CMD из каталога проекта выполните `scripts\backup.cmd`. Docker Desktop и служба `db` проекта `account-service` должны работать. Скрипт запускает `pg_dump` 17 в контейнере PostgreSQL и пишет архив custom format в `.local\backups` на диске Windows. Он проверяет код возврата, каталог объектов, полное чтение архива через `pg_restore` и SHA‑256. Только после этого каталог копии получает окончательное имя `backup-<UTC>-<id>`.

Переносите каталог целиком. В нём находятся `database.dump`, `SHA256SUMS` и `backup.json` с датой начала снимка, датой проверки, версией инструмента, размером и хешем. Успех и ошибки записываются в `backup.log` в корне копий. Код 0 означает создание проверенного архива. Любой отказ создания или проверки даёт ненулевой код. По умолчанию сохраняются 14 проверенных копий. Ротация начинается после проверки и публикации новой копии. Каталоги с неподтверждённым хешем остаются для разбирательства.

Можно задать `ACCOUNT_BACKUP_ROOT` абсолютным путём к отдельному локальному диску, `ACCOUNT_BACKUP_KEEP` числом копий и `ACCOUNT_BACKUP_MIN_FREE_MB` порогом свободного места (128 МиБ по умолчанию). Для отдельного Compose-проекта также задайте `ACCOUNT_OPS_COMPOSE_PROJECT` и `ACCOUNT_OPS_ENV_FILE`. Запуск без этих параметров работает с обычным проектом и его `.env`. Пароль в командной строке не требуется. Доступ к Docker и копиям предоставляйте только ответственному пользователю. Дамп включает пользовательские хеши паролей и данные клиентов. Для защиты от сбоя диска переносите копию в защищённое хранилище на другом носителе.

## Планировщик Windows

Запустите из обычного CMD под пользователем, которому доступен Docker Desktop.

```bat
scripts\backup-task.cmd register 02:00
scripts\backup-task.cmd run
scripts\backup-task.cmd status
```

Задание `AccountService-PostgreSQL-Backup` стартует ежедневно в указанное локальное время, с рабочей директорией проекта и обычными правами интерактивной сессии. Оно не хранит пароль Windows или PostgreSQL в аргументах. После `run` дождитесь выхода из состояния `Running`. `LastResult=0` и время последнего проверенного архива подтверждают успех. Для смены времени повторите `register` с новым значением. Регистрация останавливается при совпадении имени чужого задания. При отказе Windows в доступе используйте ручной запуск до согласования прав с администратором.

Автокопия требует активной пользовательской сессии, работающего Docker Desktop и запущенной БД. При недоступности Docker или PostgreSQL журнал получает ошибку, задача заканчивается с ненулевым кодом, последняя пригодная копия сохраняется. После восстановления доступа запустите задачу вручную и проверьте её результат.

## Изолированная проверка копии

Проверьте наличие JDK 21, Docker Desktop, собранного `target\account-service.jar`, `.env` и локального PKCS12. Если сборки ещё нет, выполните `mvnw.cmd -DskipTests package` из CMD. Остановите экземпляры, использующие этот JAR, перед новой сборкой.

```bat
scripts\restore-test.cmd
```

Для выбора конкретной копии передайте каталог первым аргументом. Без аргумента скрипт выбирает последний архив с совпадающим SHA‑256.

```bat
scripts\restore-test.cmd ".local\backups\backup-<дата-и-id>"
```

Сценарий создаёт только `account_service_restore_test` внутри нового отдельного контейнера PostgreSQL 17 с временным хранилищем и случайным портом на `127.0.0.1`. Существующая цель и любое другое имя БД отвергаются. После `pg_restore --single-transaction` скрипт проверяет миграции, ограничения, связи, аудит и равенство `current_balance = opening_balance + SUM(POSTED delta)` для всех счетов. Он запускает отдельный экземпляр JAR с уникальными паролями подключения и ждёт HTTPS readiness. Журнал, сверка и логи приложения сохраняются в `.local\restore-test\run-*`. По умолчанию сервис доступен на `https://localhost:18443/login`. Для другой учебной машины можно передать `-HttpsPort 18444`. Параметр `-Target` принимает только `account_service_restore_test`.

Войдите с учётными данными, соответствующими снимку. Сверьте число пользователей, клиентов, счетов, операций и записей аудита с протоколом создания выбранной копии. Откройте контрольный счёт, выписку за известный период и сводный отчёт. Сверьте исходящий остаток и суммы с SQL. Затем выполните `scripts\restore-test-down.cmd`. Скрипт останавливает только зарегистрированный проверочный экземпляр. Данные временной БД исчезают после остановки контейнера, а копия и журналы остаются.

Полное учебное время восстановления измеряется от объявления сбоя и поиска копии до подтверждённого входа, проверки аудита, выписки и отчёта. Сохраните обе отметки времени и дату снимка из `backup.json`. Операции, завершённые после снимка, могут потребовать отдельного восстановления из первичных документов. PostgreSQL-сеансы намеренно исключены из архива. Пользователи входят заново.

## Восстановление на другом компьютере

1. Установите JDK 21 и Docker Desktop с Linux Engine. Перенесите проверенную версию кода, каталог копии и отдельно сохранённые настройки доступа. Для восстановления владельца схемы оставьте имя роли `sourceOwner` из `backup.json`. PostgreSQL 17 берётся из Compose.
2. Подготовьте `.env` и сертификат по [руководству развёртывания](deployment.md). Конфигурация, TLS и ключи, роли сервера PostgreSQL, образы и журнал ОС в дамп не входят. Настройки и сертификаты переносите по защищённому каналу. Для существующих прикладных пользователей требуется пароль, действовавший на дату снимка.
3. Соберите JAR, выполните изолированную проверку выше и сохраните результаты. Для постоянного сервиса используйте **новый** пустой Compose-проект с новым томом и отдельным env-файлом. Запустите только `db`, чтобы штатный `docker/init-users.sql` создал роли и приложение ещё не создавало схему.
4. Из CMD задайте `ACCOUNT_OPS_COMPOSE_PROJECT` и `ACCOUNT_OPS_ENV_FILE` для нового проекта. Выполните приведённые ниже команды, подставив имя проекта, имя БД и подтверждённый архив. До восстановления убедитесь по `docker compose ps`, что открыт именно новый контур. SQL-проверка должна показать 0 таблиц в `public`. Роль `account_owner` замените на `sourceOwner`, если при копировании использовалась другая роль.

```bat
docker compose -p account-service-recovered --env-file .local\recovered.env up -d --wait db
docker compose -p account-service-recovered --env-file .local\recovered.env exec -T db psql -X -At -U account_owner -d accounts_recovered -c "select count(*) from pg_tables where schemaname='public'"
```

Если число таблиц равно 0, выполните восстановление.

```bat
docker compose -p account-service-recovered --env-file .local\recovered.env exec -T db pg_restore --exit-on-error --single-transaction -U account_owner -d accounts_recovered < "D:\verified-backup\database.dump"
```

5. Только после успешного `pg_restore` запустите приложение в этом же проекте по [руководству развёртывания](deployment.md). Flyway проверит совместимость схемы и применит новые миграции, если они нужны. Проверьте readiness, вход, связи, сальдо и аудит перед использованием новой базы. При конфликте схемы или ошибке остановитесь и проверьте версию артефакта и соответствие настроек. Для повторной попытки подготовьте ещё один чистый контур.

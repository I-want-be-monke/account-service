# Развёртывание и запуск в Windows

Понадобятся JDK 21, Docker Desktop с Linux Engine, Docker Compose v2 с поддержкой `up --wait` и CMD. Maven Wrapper загружает Maven 3.9.11 и проверяет контрольную сумму дистрибутива. Образ приложения собирает тот же проект на Maven 3.9.11 и Java 21. PostgreSQL 17.11 запускается из образа `postgres:17.11-bookworm`.

Из CMD перейдите в корень проекта и проверьте окружение.

```bat
cd /d C:\vyz\incheneria\account-service
java -version
docker info
docker compose version
mvnw.cmd -v
```

## Запуск JAR на Windows

```bat
scripts\dev-up.cmd
```

При первом запуске скрипт создаёт `.env` со случайными паролями и `.local\dev.p12` с учебным сертификатом для `localhost`. При повторном запуске используются существующие файлы. Compose ждёт готовности PostgreSQL, Maven собирает `target\account-service.jar`, Flyway применяет миграции при запуске приложения. После сообщения `Ready` откройте [страницу входа](https://localhost:8443/login). В профиле `dev` используются учётные записи `demo-admin`, `demo-operator`, `demo-accountant`, `demo-manager` и `demo-client`. Пароли находятся в локальном `.env` в полях `DEMO_*_PASSWORD`.

На Windows опубликованы только локальные порты `127.0.0.1`. PostgreSQL принимает соединения на 55432, HTTPS на 8443. HTTP на 8080 перенаправляет на HTTPS. Сертификат самоподписанный и предназначен для локальной учебной среды. Проверяйте его по отпечатку перед доверием в браузере.

```bat
type .local\logs\stdout.log
type .local\logs\stderr.log
scripts\dev-down.cmd
```

Остановка сохраняет именованный том PostgreSQL. Для полной проверки сначала остановите запущенный JAR, затем запустите `mvnw.cmd clean verify`. Windows удерживает открытый файл запущенного JAR. Maven-тесты используют отдельные контейнеры PostgreSQL.

## Полный профиль Compose

Полный профиль запускает тот же проект и базу в контейнерах. Перед переключением остановите текущий режим через `scripts\dev-down.cmd` или `scripts\full-down.cmd`. У обоих режимов с настройками по умолчанию один проект `account-service` и один том `account-service_account-data`.

```bat
scripts\full-up.cmd
docker compose -p account-service --env-file .env --profile full ps
docker compose -p account-service --env-file .env --profile full logs --tail 100 app db
scripts\full-down.cmd
```

Скрипт полного запуска готовит недостающие локальные настройки, проверяет параметры, собирает образ и ждёт статуса `healthy`. Для базового проекта он использует `.env` и `.local\dev.p12`. Пользовательский сертификат монтируется в контейнер приложения только для чтения. База доступна контейнеру по адресу `db:5432`. PostgreSQL сообщает о готовности после запуска TCP, а приложение проверяет HTTPS readiness с публичной частью смонтированного сертификата.

Для ручного запуска того же профиля с уже подготовленными `.env` и `.local\dev.p12` используйте следующую команду после остановки запущенного JAR.

```bat
docker compose -p account-service --env-file .env --profile full up --build -d --wait --wait-timeout 120 app
```

Образ собирается из `pom.xml`, исходников приложения и служебного скрипта запуска. `.dockerignore` ограничивает контекст сборки этими файлами. Сборка образа упаковывает JAR. Полный прогон `mvnw.cmd clean verify` выполняется отдельно на хосте. Пароли передаются контейнерам при запуске из окружения и локального файла настроек. Приватный ключ остаётся в локальном PKCS12. Храните исходную поставку, `.env` и сертификат в предназначенных для них местах.

Профиль `APP_PROFILE=dev` использует учебные аккаунты. Для отдельной локальной среды выберите `APP_PROFILE=pilot` и передайте `BOOTSTRAP_ADMIN_PASSWORD` через файл настроек или окружение. На пустой базе приложение создаст `bootstrap-admin` с этим паролем. После успешного входа уберите переменную из локальных настроек запуска. Имена переменных и типичные значения показаны в `.env.example`. Рабочие пароли выбирайте отдельно для каждой базы.

## Изолированный профиль для испытания

Создайте отдельный файл настроек в `.local`, заполните обязательные поля по `.env.example` и задайте отличающиеся имя БД и порты. Например, для проекта `account-service-e10-test` можно использовать следующие значения, если порты свободны.

```dotenv
DB_NAME=account_service_import_test
DB_PORT=55436
HTTP_PORT=18046
HTTPS_PORT=18446
DB_OWNER_USER=account_owner
DB_APP_USER=account_app
```

В файле должны быть также `DB_OWNER_PASSWORD`, `DB_APP_PASSWORD`, `TLS_PASSWORD` и пять `DEMO_*_PASSWORD` для `dev`. Для учебного сертификата из базовой настройки укажите соответствующий ему `TLS_PASSWORD` и передайте путь к существующему PKCS12. Сертификат должен содержать ключ с псевдонимом `accounts-local` и имя `localhost`.

```bat
scripts\full-up.cmd account-service-e10-test .local\e10-test.env .local\dev.p12
docker compose -p account-service-e10-test --env-file .local\e10-test.env --profile full ps
docker compose -p account-service-e10-test --env-file .local\e10-test.env --profile full logs --tail 100 app db
scripts\full-down.cmd account-service-e10-test .local\e10-test.env
```

Откройте `https://localhost:18446/login`. HTTP на 18046 перенаправляет на HTTPS на 18446. Именованный том `account-service-e10-test_account-data` принадлежит этому проекту. Повторный запуск с тем же именем проекта продолжает использовать его данные. Параметры можно передать и напрямую Compose через `-p`, `--env-file` и переменную `APP_TLS_FILE` с путём к PKCS12.

## Проверочный импорт

Запустите отдельный профиль, чтобы Flyway подготовил схему и создал активного бухгалтера. Соберите JAR текущей версии на хосте. Если хостовый JAR работает, сначала остановите его штатным скриптом.

```bat
mvnw.cmd -DskipTests package
scripts\import-data.cmd dry-run migration\demo-package .local\e10-test.env demo-accountant
scripts\import-data.cmd apply migration\demo-package .local\e10-test.env demo-accountant
```

Укажите каталог пакета, отдельный файл настроек и логин активного бухгалтера. Для файла импорта используйте простые строки `KEY=VALUE`. Скрипт требует отдельные имя БД и порт localhost. Команда печатает результат проверки или применения в JSON и возвращает ненулевой код при ошибке. Применяйте пакет после успешного dry-run и проверки целевых настроек. Формат файлов и контрольные суммы описаны в документации импорта.

## Резервная копия и перенос на другой компьютер

Дамп PostgreSQL хранит данные и схему БД. Для запуска на другом компьютере отдельно подготовьте исходники или проверенный JAR, локальные настройки с правами доступа, PKCS12 и параметры запуска. Дамп одной базы не включает роли всего кластера PostgreSQL и их пароли, файлы проекта, журналы приложения, настройки Windows Task Scheduler и приватный TLS-ключ.

1. Установите совместимые JDK 21 и Docker Desktop. Проверьте версию PostgreSQL из протокола копирования.
2. Перенесите копию и файл SHA-256 с сохранением доступа к защищённому месту хранения.
3. Восстановите копию в отдельную тестовую базу по инструкции восстановления и сверьте Flyway, записи, сальдо и аудит. Откройте контрольную выписку и отчёт через изолированный экземпляр приложения.
4. Используйте проверенный JAR той же версии с конфигурацией проверенной базы. Для учебного запуска подготовьте локальный сертификат для `localhost`.

Порядок резервного копирования и проверка ежедневного задания описаны в [инструкции по резервным копиям](backup.md).

## Ошибки запуска

- Если Docker Engine недоступен, запустите Docker Desktop и дождитесь готовности Linux Engine. Проверьте `docker info` из обычного CMD.
- Если порт уже занят, проверьте `docker compose ps` и текущий запуск JAR. Переключитесь штатной командой остановки или выберите отдельные порты для изолированного проекта.
- При ошибке готовности проверьте журналы приложения и БД. Ошибка Flyway или недоступность PostgreSQL видна до готовности приложения.
- При ошибке сертификата проверьте путь PKCS12, срок действия, псевдоним ключа и соответствие `TLS_PASSWORD`. Существующий файл заменяйте только после сохранения копии и проверки нового сертификата.

Для показа преподавателю запустите нужный режим, войдите под учебной ролью, сформируйте выписку и отчёт и покажите готовность PostgreSQL и приложения. Отдельный проект подходит для демонстрации импорта, повторного запуска и сверки восстановленных данных.
